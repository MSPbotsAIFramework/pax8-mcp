## Requirement understanding

One line: Add a pax8_update_subscription tool to the Pax8 MCP so quantity (and billingTerm/startDate/endDate) can be changed on an existing Pax8 subscription, matching the Rewst "Purchase/Remove License" automation Ginko IT runs today.

This is item 31 of the Rewst→MSPbots migration gap list (`mspbots-gap-register.xlsx`), filed as a "tool gap" against an existing connector, not a new integration. The requester wants parity with Rewst's `pax8.update_subscription` action: a way to change a subscription's seat count (and, incidentally, its billing term / start date) so an Agent can add or remove M365 licenses the way the Ginko IT Rewst flows do today (11 "Purchase License" + 4 "Remove License" runs in the last 365 days, evidence grade B). The ticket supplies the exact Pax8 endpoint (`PUT /v1/subscriptions/{subscription_id}`), the field list, and a sample Rewst request body — this is a well-specified tool addition, not an open design question.

- The service exposes 9 tools today, all read-only `list_*` calls, registered from six modules (`companies.py`, `invoices.py`, `orders.py`, `products.py`, `subscriptions.py`, `usage.py`) via `server.py:116-123`. README confirms the same 9-tool table (`README.md`, "Tool List" section) — matches the ticket's own note that all 9 existing tools are list operations.

## Product design

### Goals / Non-goals

**Goals:**
- Expose Pax8's `PUT /v1/subscriptions/{subscription_id}` endpoint as a new MCP tool, `pax8_update_subscription`, so an Agent (or anything driving this MCP with a valid Pax8 credential) can change a subscription's quantity, and optionally its billing term, start/end dates, pricing, and provisioning details — the same capability Ginko IT's Rewst flows use today for M365 license add/remove.
- Keep the new tool indistinguishable in shape, error handling, and documentation style from the 9 existing tools, so a caller (human or Agent) cannot tell which tools were added when.

**Non-goals:**
- Does not fix the platform connector's OAuth callback registration defect (wiki `_connector-fields.md § P-2`, open gap #4b) that currently blocks `connect.mspbots.ai` users from authorizing Pax8 at all. That is a gateway/OAuth-application configuration issue outside this repo; it affects the other 9 tools identically and is already tracked separately.
- Does not add create/delete-subscription tools, or write tools for any other resource (companies, invoices, orders, products, usage). Scope is exactly the one tool the ticket names.
- Does not add retry/backoff/timeout handling to `Pax8Client` beyond what `get()` already has (none). That gap is repo-wide and pre-existing (see Risks).

### Acceptance criteria AC1..AC6

- **AC1** — Given a valid `subscription_id`, `quantity`, and a valid Pax8 credential (header in gateway mode, `PAX8_API_TOKEN` in env mode), when `pax8_update_subscription` is called, then the tool sends `PUT /v1/subscriptions/{subscription_id}` with the provided fields in the request body and returns the updated subscription (as returned by Pax8: at minimum `id`, `quantity`, `status`, `billingTerm`) as a JSON string.
- **AC2** — Given optional fields (`billingTerm`, `startDate`, `endDate`, `price`, `partnerCost`, `currencyCode`, `provisioningDetails`) that are not passed to the tool, when `pax8_update_subscription` is called, then those fields are omitted from the outbound PUT body entirely (not sent as `null`), so attributes the caller did not mention are left unchanged on the Pax8 side.
- **AC3** — Given no Pax8 credential is available (missing gateway header, or no `PAX8_API_TOKEN` in env mode), when `pax8_update_subscription` is called, then it returns the same `_NO_TOKEN` message the 9 existing tools already return, and makes no call to the Pax8 API.
- **AC4** — Given the Pax8 API rejects the request (any 4xx or 5xx, e.g. an unknown `subscription_id` or an invalid `billingTerm` value), when `pax8_update_subscription` is called, then it returns `Error {status_code}: {message}` — the exact string format the other 9 tools already use — and never raises an unhandled exception.
- **AC5** — Given two concurrent calls to `pax8_update_subscription` carrying two different tenants' credentials, when both run at the same time, then each call uses only its own credential and neither call's Pax8 request can carry the other tenant's token (the existing per-request `contextvars` isolation is not weakened by the new tool).
- **AC6** — Given the README's "Tool List" table, when this ticket is done, then it lists `pax8_update_subscription` with a description and key parameters in the same row shape as the other 9 tools, and the "Parameter Details" section documents the `billingTerm` enum.

### Open questions

- None that block implementation. One judgment call, not a product question: `billing_term` is typed as a plain `str | None` (documented via an enum list in the docstring), matching how the existing `status` parameter on `pax8_list_subscriptions` is done (`subscriptions.py:28-29`) rather than a `Literal[...]` type — consistency with the sibling tool in the same file, not a product decision. Does not block; stated here for the record.

## Tech design

### Conclusion

Add one method to the shared HTTP client (`Pax8Client.put`) and one new tool function in the existing `subscriptions.py` module, following the exact shape (credential check, try/except, error-string format) already used by all 9 tools in this repo. No new files other than tests; no change to any of the 8 other tools, to `server.py`'s registration list, or to the auth/middleware layer.

### Where the current implementation lives

- `src/pax8_mcp/api_client.py:16-59` — `Pax8Client`, currently `get()`-only.
- `src/pax8_mcp/tools/subscriptions.py:1-75` — the module this ticket's new tool belongs in (subscription resource).
- `src/pax8_mcp/server.py:116-123` — tool-module registration (unchanged; `subscriptions.register(mcp, client_factory)` already wires in whatever `subscriptions.py` registers).
- `README.md` "Tool List" / "Parameter Details" sections — needs one new row + one new enum note.

### Option analysis

- **Add `put()` to the shared `Pax8Client`** (chosen) vs. building a one-off `httpx` call inside the tool function. Rejected the one-off: the client already centralizes headers, base URL, and error mapping (`_headers`, `_raise_for_status`); duplicating that in the tool function would be the first owner of two copies of the same logic in this repo.
- **Put the new tool in `subscriptions.py`** (chosen) vs. a new `tools/subscription_writes.py` module. Rejected a new file: the repo splits tool modules by *resource* (companies, invoices, orders, products, subscriptions, usage), not by read/write; a subscription-write tool belongs with the other subscription tool. No other module in this repo separates reads from writes.
- **Client-side validation of `billingTerm` against the enum** vs. pass-through. Chose pass-through (reject only what Pax8 itself rejects): the sibling `status` parameter on `pax8_list_subscriptions` already documents its enum in the docstring without enforcing it in code (`subscriptions.py:28-29`); adding enforcement only for the new tool would be inconsistent within the same file, and Pax8's own 400 response for an invalid value is already surfaced correctly via AC4.
- **PUT with only the provided fields** (chosen, via the existing `_clean_params` filter reused for the body) vs. always sending the full field set. The ticket's own Rewst sample body sends only `quantity`, `startDate`, `billingTerm`, `provisioningDetails` — not every field — which only makes sense if Pax8 treats absent fields as "leave unchanged" rather than "reset to null". Sending `null` for unset optional fields risks silently clearing a subscription's price, currency, or dates whenever a caller only means to change the quantity. `_clean_params` (`api_client.py:38-41`) already does exactly this filtering for query params; reusing it for the body is the same fix applied to the same kind of input.

### Change list

1. **`src/pax8_mcp/api_client.py`** — add:
   ```python
   async def put(self, path: str, json_body: dict | None = None) -> Any:
       async with httpx.AsyncClient() as client:
           resp = await client.put(
               f"{self._base_url}{path}",
               headers=self._headers(),
               json=self._clean_params(json_body),
           )
           self._raise_for_status(resp)
           return resp.json() if resp.status_code != 204 else None
   ```
   Mirrors `get()` line for line (same client-per-call pattern, same header/error handling); reuses `_clean_params` to drop `None` values from the JSON body before sending.

2. **`src/pax8_mcp/tools/subscriptions.py`** — add a third tool inside `register()`:
   ```python
   from mcp.types import ToolAnnotations

   @mcp.tool(
       annotations=ToolAnnotations(
           readOnlyHint=False, destructiveHint=True, idempotentHint=True,
       )
   )
   async def pax8_update_subscription(
       subscription_id: str,
       quantity: int,
       billing_term: str | None = None,
       start_date: str | None = None,
       end_date: str | None = None,
       price: float | None = None,
       partner_cost: float | None = None,
       currency_code: str | None = None,
       provisioning_details: list[dict[str, str]] | None = None,
   ) -> str:
       """Update a Pax8 subscription's quantity, billing term, or dates.

       This changes the customer's live subscription and billing in Pax8.
       Confirm the new quantity and terms with the requester before calling.
       Fields you omit keep their current value; only the fields you pass change.

       Args:
           subscription_id: The unique identifier of the subscription to update.
           quantity: New total seat/license count for the subscription.
           billing_term: One of: Monthly, Annual, 2-Year, 3-Year, 1-Time, Trial.
           start_date: New start date (ISO 8601, e.g. "2026-11-01").
           end_date: New end date (ISO 8601).
           price: New unit price.
           partner_cost: New partner cost.
           currency_code: ISO currency code, e.g. "USD".
           provisioning_details: List of {"key": ..., "value": ...} entries.
       """
       client = client_factory()
       if client is None:
           return _NO_TOKEN
       try:
           result = await client.put(
               f"/subscriptions/{subscription_id}",
               json_body={
                   "quantity": quantity,
                   "billingTerm": billing_term,
                   "startDate": start_date,
                   "endDate": end_date,
                   "price": price,
                   "partnerCost": partner_cost,
                   "currencyCode": currency_code,
                   "provisioningDetails": provisioning_details,
               },
           )
           return json.dumps(result, indent=2)
       except Pax8Error as e:
           return f"Error {e.status_code}: {e.message}"
   ```

### Data & API contract

Outbound (Pax8 Partner API, called from the tool):

```
PUT https://api.pax8.com/v1/subscriptions/{subscription_id}
Authorization: Bearer <token>
Content-Type: application/json

{
  "quantity": 25,
  "billingTerm": "Monthly",
  "startDate": "2026-11-01",
  "provisioningDetails": []
}
```
(only the keys the caller provided a value for; absent keys are not sent — AC2)

Tool-facing (MCP):

```
tools/call pax8_update_subscription
{
  "subscription_id": "11111111-2222-3333-4444-555555555555",
  "quantity": 25,
  "billing_term": "Monthly",
  "start_date": "2026-11-01"
}
-> "{\n  \"id\": \"11111111-...\",\n  \"quantity\": 25,\n  \"status\": \"Active\",\n  \"billingTerm\": \"Monthly\"\n}"
```

Error path (any Pax8 4xx/5xx):
```
-> "Error 404: {\"message\": \"Subscription not found\"}"
```
No credential:
```
-> "Error: No Pax8 token configured. Set PAX8_API_TOKEN or use AUTH_MODE=gateway."
```

Backward compatibility: purely additive — no existing tool's name, parameters, or return shape changes; `tools/list` grows from 9 entries to 10.

### Key flow / sequence

1. Agent/client sends `tools/call pax8_update_subscription {...}` over `/mcp`, carrying `X-Pax8-Token` (gateway mode).
2. `GatewayTokenMiddleware` reads the header into the per-request `contextvars.ContextVar` (unchanged, `server.py:36-79`).
3. `client_factory()` resolves a fresh `Pax8Client` from that contextvar (unchanged, `server.py:24-33`).
4. The new tool builds the body dict, calls `client.put(f"/subscriptions/{subscription_id}", json_body={...})`.
5. `Pax8Client.put` filters `None` values out of the body (`_clean_params`), sends `PUT`, raises `Pax8Error` on non-2xx.
6. Tool returns either the JSON-encoded updated subscription, the `_NO_TOKEN` string, or the `Error {code}: {message}` string.

### Non-functional

- **Multi-tenant isolation**: unchanged — the new tool uses the same per-request `contextvars` credential path as all 9 existing tools; no new global/module-level state is introduced (AC5).
- **Idempotency / safety**: `PUT` with the same body twice produces the same end state, so `idempotentHint=True`; it mutates live billing data and is not reversible from inside this MCP (no corresponding "undo" call), so `destructiveHint=True`; `readOnlyHint=False`. Per SOP §2.7, the docstring states the consequence ("changes the customer's live subscription and billing") up front so a calling Agent can decide whether to confirm with a human first.
- **Performance**: single outbound call, no pagination involved; same per-call client construction cost as every existing tool (no regression, no improvement — see Reuse & cleanup for the pre-existing no-timeout/no-reuse gap).
- **Security**: credential handling is unchanged (Header-only, never persisted, never logged); no new credential type or header is introduced.
- **Logging/observability**: no new logging added beyond what the shared client/middleware already does; no plan to log request bodies (they can carry pricing fields).

### Rollout & rollback

- **Rollout**: purely additive change, merged into `master` and published to INT in the review leg (`mcppub publish`). No feature flag needed — a new tool appearing in `tools/list` does not change the behavior of any existing tool or any already-integrated Agent flow.
- **Rollback**: if the new tool misbehaves on INT, redeploy the pre-merge `master` sha via the same publish path; because the change is additive and touches no shared state, rollback carries no data-migration or compatibility concern.
