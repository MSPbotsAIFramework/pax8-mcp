## Requirement understanding

One line: add a Pax8 MCP tool that fetches a single subscription by id (quantity, billingTerm, productId, companyId, etc.), closing gap item 32 of the Rewst-to-MSPbots migration gap register.

The gap register (`mspbots-gap-register.xlsx`, item 32, evidence level B, account "Ginko IT") records that Rewst's `pax8.get_subscription` action — `GET /v1/subscriptions/{subscription_id}` — has no equivalent in the `pax8-mcp` tool set: today `pax8-mcp` only exposes list/search-shaped tools, none of which return a single subscription by id. Success is a new `pax8_get_subscription` tool that lets an agent resolve one subscription's detail (status, billing term, product, company, dates, price) given its id, the same data Rewst's flow consumed.

Sources: ticket description (unchanged since filing, checked 2026-10-30) · code read-only verified: `src/pax8_mcp/tools/*.py`, `src/pax8_mcp/api_client.py`, `src/pax8_mcp/server.py`, `README.md` (all at `master`@f71ce7a) · wiki: `ProductDocs/_connector-fields.md` § P-2 (`_verified_` 2026-08-31, v4.1.518) — see "Current state" below; no other wiki page covers Pax8 or this tool set (`wiki find pax8` otherwise only surfaces the same P-2 item and unrelated gap-queue/patrol-log mentions).

## Current state (every claim carries path:line)

`MSPbotsAIFramework/pax8-mcp` is a stateless HTTP MCP service wrapping the Pax8 partner REST API (`https://api.pax8.com/v1`). It registers 9 tools today, all of them list/collection-shaped:

- `pax8_list_companies`, `pax8_list_company_contacts` — `src/pax8_mcp/tools/companies.py`
- `pax8_list_subscriptions`, `pax8_list_subscription_usage_summaries` — `src/pax8_mcp/tools/subscriptions.py:13-74`
- `pax8_list_invoices`, `pax8_list_invoice_items` — `src/pax8_mcp/tools/invoices.py`
- `pax8_list_orders` — `src/pax8_mcp/tools/orders.py`
- `pax8_list_products` — `src/pax8_mcp/tools/products.py`
- `pax8_list_usage_summary_lines` — `src/pax8_mcp/tools/usage.py`

Every tool follows the same shape: call `client_factory()` (`src/pax8_mcp/server.py:24-33`, resolves a `Pax8Client` from either the gateway per-request contextvar or `PAX8_API_TOKEN` env var), return the fixed `_NO_TOKEN` string if there is no client, otherwise `await client.get(<path>, params=...)` and `json.dumps(result, indent=2)`, catching `Pax8Error` and returning `f"Error {e.status_code}: {e.message}"` (`src/pax8_mcp/tools/subscriptions.py:32-49`). `Pax8Client.get()` (`src/pax8_mcp/api_client.py:43-51`) is already fully generic — any path, optional query params, bearer-token auth injected per call — so GET-by-id is not a new capability for the client, only for the tool layer.

There is no single-subscription-by-id tool. `pax8_list_subscriptions` (`src/pax8_mcp/tools/subscriptions.py:13-49`) can filter by `company_id`/`product_id`/`status` but not by subscription id, and it returns a page of results, not one record. This matches the ticket's own observation ("`api_client` only has `get()`, all 9 tools are list").

`server.py:115-121` registers all tool modules unconditionally (no feature flags); any new `@mcp.tool()` function added inside `subscriptions.register()` is picked up automatically, no other wiring needed.

There is no `tests/` directory in the repo despite `pyproject.toml:27` (`testpaths = ["tests"]`) and `pytest`/`pytest-asyncio`/`respx` already listed as dev dependencies (`pyproject.toml:24-29`) — no tool in this repo has an automated test today.

**Separate, pre-existing platform issue (not in scope for this ticket):** `wiki: ProductDocs/_connector-fields.md § P-2 (_verified_ 2026-08-31, v4.1.518)` records that connecting the Pax8 connector card on the platform currently fails with `error=unauthorized_client / Callback URL mismatch` — the Pax8 OAuth app does not have the platform's callback URL registered, so no tenant can complete a live Pax8 connection today. The ticket description itself references this ("platform card currently returns unauthorized_client (docs)"). This blocks end-to-end testing with a real Pax8 account; it does not block adding the tool, since the gap is in connector registration/OAuth config, not in `pax8-mcp`'s code.

## Product design

### Goals / Non-goals

- Goal: add one new read-only MCP tool, `pax8_get_subscription(subscription_id)`, that returns the full Pax8 subscription record for a given id.
- Goal: keep the tool indistinguishable in shape, error handling, and auth behavior from the other 9 tools in this repo — an agent/operator should not be able to tell it was added later.
- Non-goal: no change to how subscriptions are listed/filtered (`pax8_list_subscriptions` is untouched).
- Non-goal: no change to credential handling, transport, or the gateway contract (Section "Non-functional" below).
- Non-goal: fixing the Pax8 connector's OAuth callback-URL registration (wiki P-2) — tracked as a pre-existing, separate platform issue, not this ticket's scope.

### Acceptance criteria AC1..AC6

- AC1: Given a Pax8 token with access to subscription `{id}`, when an MCP client calls `pax8_get_subscription(subscription_id="{id}")`, then the tool returns the JSON body of `GET /v1/subscriptions/{id}` from Pax8 (pretty-printed, pass-through — not reshaped or filtered), the same way every other tool in this repo returns Pax8's response as-is.
- AC2: Given a `subscription_id` that Pax8 rejects (not found, or no access — Pax8 responds with a 4xx/5xx), when the tool is called, then it returns the string `Error {status_code}: {message}` (same format as every other tool), not a raw exception or a 500 to the MCP client.
- AC3: Given no Pax8 credentials are available for the request (env mode with no `PAX8_API_TOKEN` set, or gateway mode with no auth header on the request), when the tool is called, then it returns the existing `_NO_TOKEN` message verbatim — no new "missing credentials" message is introduced.
- AC4: Given the README's "Tool List" table, when this ticket ships, then the table has one new row for `pax8_get_subscription` with its key parameter (`subscription_id`), in the same row format as the other 9 tools.
- AC5: Given two concurrent gateway-mode requests carrying two different `X-Pax8-Token` values, when one or both call `pax8_get_subscription`, then each request's outbound call to Pax8 uses only the token resolved for that request's own context — no cross-request token leakage. (This is an existing guarantee of `server.py`'s per-request contextvar, not new work; it's listed as an AC because it is the multi-tenant/isolation check this ticket must not regress.)
- AC6: Given `tools/list` is called after this ticket ships, when the client inspects the tool definitions, then `pax8_get_subscription` is listed with exactly one required parameter, `subscription_id` (string).

### Open questions

- [non-blocking] Should `subscription_id` be explicitly URL-encoded before being interpolated into the path? Default: no — the sibling tool `pax8_list_subscription_usage_summaries` (`src/pax8_mcp/tools/subscriptions.py:68-70`) builds its path the same unescaped way, and Pax8 subscription ids are UUIDs in practice. Flagged as a possible follow-up for the whole module (all `*_id`-in-path tools), not fixed in this ticket — it is a pre-existing pattern, not something introduced here.

## Tech design

### Conclusion

Add one read-only MCP tool, `pax8_get_subscription(subscription_id: str)`, to the existing `tools/subscriptions.py` module. It reuses the already-generic `Pax8Client.get()` (no API-client change needed) and the exact error/no-credentials handling every other tool in this repo already uses — so this is a same-shape addition, not a new mechanism. The only other change is a README table row and the repo's first test file.

### Where the current implementation lives

- `src/pax8_mcp/tools/subscriptions.py:11-74` — the module this tool belongs in; `register()` is called unconditionally from `server.py:119`.
- `src/pax8_mcp/api_client.py:43-51` — `Pax8Client.get(path, params=None)`, already generic enough for `GET /subscriptions/{id}` with no params.
- `src/pax8_mcp/tools/subscriptions.py:51-74` (`pax8_list_subscription_usage_summaries`) — closest analog: single-subscription-scoped tool that builds an f-string path with the id, same error handling. The new tool is modeled on this one, minus the `params`/pagination.
- `src/pax8_mcp/server.py:91-96` — the `_NO_TOKEN` diagnostic-only path when no credentials exist at all; unaffected, just reused.
- `README.md:105-114` — the Tool List table to extend.

### Option analysis

No real alternative: the client is already generic, the tool pattern is already established by 9 other tools, and the only shape decision (pass through Pax8's JSON verbatim vs. reshape to the field subset the ticket lists) is answered by precedent — every existing tool passes the Pax8 response through untouched (`json.dumps(result, indent=2)`), so there is no per-tool response schema to maintain or keep in sync with Pax8's API. Reshaping would be new, bespoke behavior with no precedent in this repo and no stated need (the ticket's field list — `id`, `companyId`, `productId`, `quantity`, `status`, `billingTerm`, `startDate`, `endDate`, `price` — is a description of what the caller cares about, not a contract to enforce; Pax8's actual response may include more fields, and passing them through is strictly more useful, not less).

### Change list

- `src/pax8_mcp/tools/subscriptions.py` [changed] — add:
  ```python
  @mcp.tool()
  async def pax8_get_subscription(subscription_id: str) -> str:
      """Get a single Pax8 subscription by id.

      Args:
          subscription_id: The unique identifier of the subscription.
      """
      client = client_factory()
      if client is None:
          return _NO_TOKEN
      try:
          result = await client.get(f"/subscriptions/{subscription_id}")
          return json.dumps(result, indent=2)
      except Pax8Error as e:
          return f"Error {e.status_code}: {e.message}"
  ```
  placed inside the same `register()` function, after `pax8_list_subscriptions` and before `pax8_list_subscription_usage_summaries` (keeps the file's existing "list, then usage" reading order, with the new single-get tool next to the list tool it complements).
- `README.md` [changed] — add one row to the "Tool List" table (`README.md:105-114`):
  `| \`pax8_get_subscription\` | Get a single subscription by id | \`subscription_id\` |`
  placed directly after the `pax8_list_subscriptions` row, before `pax8_list_subscription_usage_summaries`, matching the change above.
- `tests/__init__.py`, `tests/test_subscriptions.py` [new] — first test file in the repo (see "Test strategy").
- `src/pax8_mcp/api_client.py` — no change: `Pax8Client.get(path)` already accepts a bare path with no query params.
- `src/pax8_mcp/server.py` — no change: `subscriptions.register(mcp, client_factory)` (`server.py:119`) already wires the whole module; a new `@mcp.tool()` inside it needs no separate registration.

- New dependencies: none for the implementation. `pytest`, `pytest-asyncio`, `respx` are already declared in `pyproject.toml:24-29` (dev group) but unused until this ticket's tests — no new package added.
- Interface/contract: new MCP tool `pax8_get_subscription(subscription_id: str) -> str`. One required string parameter, matching the convention every other single-resource tool in this repo uses (`pax8_list_subscription_usage_summaries`, `pax8_list_invoice_items`, `pax8_list_usage_summary_lines`).
- In-scope cleanup: none found in `subscriptions.py` or the files this ticket touches — the module is small (74 lines) and the two existing tools are not duplicated or dead.
- Follow-ups (out of scope for this ticket): (1) the whole `pax8-mcp` repo has zero tests — this ticket adds the first one, scoped to the new tool; back-filling tests for the other 9 tools is a separate, larger ticket. ### Data & API contract

- MCP tool: `pax8_get_subscription(subscription_id: str) -> str` (JSON string on success, `"Error {code}: {message}"` string on failure, `_NO_TOKEN` string if uncredentialed — three possible return shapes, all plain strings, matching every other tool in this repo; MCP tool results are always strings here, there is no structured-error channel to add).
- Upstream call: `GET https://api.pax8.com/v1/subscriptions/{subscription_id}` with `Authorization: Bearer <token>` (unchanged header injection, `api_client.py:32-36`). No query parameters.
- Response: Pax8's JSON body is returned verbatim (pretty-printed). Per the ticket, callers care about `id`, `companyId`, `productId`, `quantity`, `status`, `billingTerm`, `startDate`, `endDate`, `price` — all of these are passed through with whatever else Pax8 includes; no field is dropped or renamed.
- Errors: Pax8 4xx/5xx → `Pax8Error(status_code, message)` → tool returns `f"Error {status_code}: {message}"` (e.g. a non-existent id most likely 404s upstream; exact Pax8 error body not independently verified in this design pass — same uncertainty already exists for every other tool in the repo, since none of them special-case Pax8's error payload shape).
- Backward compatibility: purely additive (new tool, new README row); no existing tool's behavior, parameters, or response shape changes.
- DB: none — this service has no database.

### Key flow / sequence

1. MCP client sends `tools/call` for `pax8_get_subscription` with `subscription_id`.
2. `server.py` middleware/env resolution (unchanged) makes a `Pax8Client` available via `client_factory()`.
3. New tool function calls `client.get(f"/subscriptions/{subscription_id}")`.
4. `Pax8Client.get()` issues `GET {base_url}/subscriptions/{subscription_id}` with the resolved bearer token.
5. 2xx → tool returns `json.dumps(result, indent=2)`. 4xx/5xx → `Pax8Error` raised and caught → tool returns the formatted error string. No credentials → step 2 never produces a client, tool returns `_NO_TOKEN` before any HTTP call is made.

### Non-functional

- Idempotency & concurrency: `GET` is naturally idempotent; no shared mutable state is touched (each call opens its own `httpx.AsyncClient`, `api_client.py:44`), so concurrent calls for different or the same `subscription_id` do not interfere.
- Performance: single HTTP round-trip, same cost profile as `pax8_list_subscription_usage_summaries`; no pagination, no N+1 risk.
- Security: no new credential path — token still comes from the per-request gateway contextvar or the env var, exactly as for the 9 existing tools (`server.py:24-33`, `:60-75`); nothing is logged, written to disk, or echoed back by this tool (same as the rest of the repo).
- Multi-tenant isolation: enforced upstream of this tool, by `GatewayTokenMiddleware` setting a per-asyncio-task contextvar per request (`server.py:38-75`) — this ticket adds no new shared state, so the existing isolation guarantee (AC5) is preserved by construction, not by anything new in this tool.
- Observability: no tool in this repo logs at the call level today (a pre-existing, repo-wide gap, not introduced or fixed by this ticket); errors are visible to the caller via the returned error string, consistent with every other tool.

### Rollout & rollback

- No feature flag: the tool becomes available the moment the new container image is deployed (same as any other tool addition in this repo — `server.py` registers all tools unconditionally).
- No DB migration, no data backfill, no credential/config change.
- Rollout: per `references/mcp-track.md` §3–4 — develop on `dev/PRD-21600` off the default branch `master`, merge, `uv run pytest` must pass on the merged code, then publish to INT via `mcppub publish --repo MSPbotsAIFramework/pax8-mcp` (already-registered vendor, not a new one — no `mcppub register` step needed).
- Rollback: revert the merge commit and redeploy; purely additive, read-only change, so rollback leaves no state to clean up.
- Cross-repo release order: none — this ticket touches exactly one repo (`pax8-mcp`) and introduces no header/field that another repo needs to understand; `release order: any` is moot (single repo).

### Test strategy

- Unit tests (new `tests/test_subscriptions.py`, using the already-declared `pytest-asyncio` + `respx` dev dependencies to mock `httpx` against `https://api.pax8.com/v1`):
  - Happy path: `respx` mocks `GET /v1/subscriptions/{id}` → 200 with a representative JSON body; assert the tool returns that JSON pretty-printed, unmodified.
  - Error path: `respx` mocks a 404 (or 4xx) response; assert the tool returns `"Error 404: ..."` (mirrors AC2).
  - No-credentials path: call the tool with a `client_factory` that returns `None`; assert it returns the exact `_NO_TOKEN` string, no HTTP call attempted (mirrors AC3).
- Manual/semi-automated: `initialize` → `tools/list` smoke check (per `references/mcp-track.md` §3.2 step 7) to confirm `pax8_get_subscription` is listed with the expected single required parameter (AC6).
- Needs a real vendor account (not run by this ticket, per `references/mcp-track.md` §2.5 — missing a test account is not a blocker): AC5's cross-request isolation and AC1's true end-to-end call against live Pax8 cannot be exercised with a real tenant right now, because the Pax8 connector's OAuth registration is broken platform-wide (wiki § P-2) — no tenant can complete a Pax8 connection to obtain a real token. AC5 is still covered at the unit level by the existing contextvar mechanism (unchanged by this ticket); flagged here as the regression surface, not as untested.
- Regression surface: the other 8 tools and the client are unmodified; the only shared file touched is `subscriptions.py`, and the new function doesn't call or depend on the two existing ones in that file.
