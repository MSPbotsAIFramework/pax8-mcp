## Requirement understanding

One line: Add a `pax8_get_company` tool to the Pax8 MCP connector that fetches a single company by its Pax8 company id (GET `/v1/companies/{company_id}`), matching the Rewst `pax8.get_company` action used in the Ginko IT "Licences: Update Quantity" flow.

This ticket comes from the Rewst → MSPbots migration gap register (`mspbots-gap-register.xlsx`, item 34). It is a "tool" gap: the Pax8 connector already exists in MSPbotsAIFramework, but it is missing the one tool needed to replicate a specific Rewst action (`pax8.get_company`) that an existing Rewst flow (Ginko IT, "Licences: Update Quantity") calls. Success is: the new tool exists, takes a Pax8 `company_id`, and returns the company record (at minimum `id`, `name`, `status`, `externalId`) the same way Rewst's action does, so that flow can be rebuilt on MSPbots without a capability gap.

## Current state

- `MSPbotsAIFramework/pax8-mcp` is a stateless, per-request-auth MCP service for the Pax8 Partner API (`README.md:1-3`, `README.md:77-101`). It registers 9 tools today, all list/collection-shaped (`src/pax8_mcp/tools/companies.py:13`, `:40`; `src/pax8_mcp/tools/subscriptions.py:13`, `:52`; `src/pax8_mcp/tools/invoices.py:13`, `:48`; `src/pax8_mcp/tools/orders.py:13`; `src/pax8_mcp/tools/products.py:13`; `src/pax8_mcp/tools/usage.py:13`; confirmed against the Tool List table, `README.md:105-115`). None of them fetches a single company by id — `pax8_list_companies` (`src/pax8_mcp/tools/companies.py:13-37`) only lists/filters by name, and `pax8_list_company_contacts` (`:40-62`) fetches a company's contacts, not the company record itself. This matches the ticket's own evidence ("`api_client` 只有 `get()`，9 个工具全是 list").
- `Pax8Client` (`src/pax8_mcp/api_client.py:16-59`) is a thin async wrapper: one generic `get(path, params)` method (`:43-51`) that sends `Authorization: Bearer <token>` and raises a structured `Pax8Error(status_code, message)` on any 4xx/5xx (`:53-59`). Adding a new read-only GET tool requires no change to this client — the existing `get()` already supports an arbitrary path such as `/companies/{company_id}`.
- Auth is per-request and stateless: in `gateway` mode (production default, `src/pax8_mcp/config.py:21`), `GatewayTokenMiddleware` (`src/pax8_mcp/server.py:36-79`) reads the `X-Pax8-Token` header on every `/mcp` request, stores the raw token in a `contextvars.ContextVar` scoped to that request/task (`:19-21`, `:75-79`), and rejects the request with 401 before any tool runs if the header is missing (`:61-73`). So a new tool automatically inherits this isolation and this "no token → 401 before the tool body runs" behavior; in `env` mode (local dev only) a missing token instead produces the tool-level `_NO_TOKEN` string ("Error: No Pax8 token configured...", `src/pax8_mcp/tools/companies.py:8`), exactly as the two existing company tools already handle it.
- `pyproject.toml:22-30` declares `pytest`, `pytest-asyncio`, `respx` (an httpx mock library) as dev dependencies and `pyproject.toml:35-36` points `testpaths` at `tests/`, but **no `tests/` directory exists in this repo today** (confirmed: no files matched under the repo root other than `src/`). This is a pre-existing gap, not something this ticket caused — noted here because it means this ticket is also the first to add a test file to this repo.
- Separately, the product wiki records a platform-level defect: clicking the Pax8 connector's "+" in the Agent platform currently returns `error=unauthorized_client` / "Callback URL mismatch" because the OAuth callback URL is not registered on Pax8's side (wiki: `ProductDocs/_connector-fields.md` § "P-2 · Pax8 连不上（产品缺陷，不是文档问题）"). That defect is about the platform's OAuth **connect** flow (MCP Management Service ↔ Pax8), which is unrelated code to this MCP server: `pax8-mcp` never performs the Pax8 OAuth handshake itself — it only reads a bearer token already handed to it via `X-Pax8-Token` (gateway mode) and forwards it (`src/pax8_mcp/api_client.py:33-34`). The new tool uses the exact same request path as the 9 existing tools, so it is neither more nor less affected by that defect than they are. See Risks & dependencies.

## Product design

### Goals / Non-goals

- Goal: add one new MCP tool, `pax8_get_company`, that fetches a single Pax8 company by id and returns it as JSON, usable the same way the 9 existing tools are used (gateway-mode header auth, or env-mode local token).
- Goal: keep the new tool consistent with the existing tools' conventions (naming, error handling, docstring style, README Tool List entry) so it does not read as a one-off.
- Non-goal: fixing the Pax8 OAuth "Callback URL mismatch" connect-flow defect (wiki P-2). That is a platform/control-plane (MCP Management Service) registration issue, not a vendor-repo code change, and is out of scope for this ticket (see Risks & dependencies).
- Non-goal: adding any other missing Pax8 capability beyond `pax8_get_company`. The gap register item (#34) names exactly this one tool; no other gap for this connector is in scope here.
- Non-goal: field filtering/projection. The tool returns the full company object the Pax8 API returns, not just the four fields the Rewst flow happens to use (see Tech design § Data & API contract, and Open questions).

### Acceptance criteria

- AC1: Given a valid Pax8 token and an existing `company_id`, when `pax8_get_company` is called, then it returns the company record as JSON (including at minimum `id`, `name`, `status`, `externalId`) — the same way the existing list tools return Pax8 API responses verbatim.
- AC2: Given a `company_id` that does not exist (Pax8 API returns 404), when `pax8_get_company` is called, then the tool returns a structured error string in the same shape the existing tools use for API errors (`"Error {status_code}: {message}"`), and does not raise an unhandled exception.
- AC3: Given the server is running in `env` auth mode with no `PAX8_API_TOKEN` configured, when `pax8_get_company` is called, then it returns the same "No Pax8 token configured" diagnostic message the two existing company tools return, not a crash or an empty result.
- AC4: Given the MCP server has started with credentials available, when a client calls `tools/list`, then `pax8_get_company` appears in the list with a `company_id` (string, required) parameter, alongside the existing 9 tools (10 total).
- AC5 (manual, needs a real Pax8 partner account): Given a real Pax8 partner token and a known real `company_id`, when `pax8_get_company` is called through a running `/mcp` endpoint, then the response contains that company's actual `id`, `name`, `status`, and `externalId`. Per the pipeline's completion rule for vendor-mcp tickets, the absence of a real test account at dev/self-test time does not block the ticket; this case is recorded and marked "needs a real vendor account" until one is available.

### Open questions

- [已假设] Response shape: the ticket's evidence table only names the fields the Rewst flow reads (`id`, `name`, `status`, `externalId`), but none of the 9 existing tools in this repo trim or reshape the Pax8 API response — they all return `json.dumps(result, indent=2)` of whatever Pax8 returns. This design assumes the new tool follows that same convention (return the full company object), rather than introducing the first field-filtering logic in this repo. If a narrower contract is actually required (e.g. to reduce token usage for the AI client), AC1's wording would need to be tightened and this would be a small, low-risk follow-up to the same function — it does not change where the code lives.
- [不阻塞] Exact full response schema: the Pax8 public API reference page linked from the README (`https://devx.pax8.com/reference/findcompanies`) documents `GET /companies` (list) but its "get one company by id" page was not directly reachable during this design (see Tech design § Data & API contract for what was confirmed vs. inferred). This does not block implementation — the dev leg should capture the live response shape from a real call (or from `respx`-recorded fixtures) and use that for the auto test's fixture; the ticket's named fields (`id`, `name`, `status`, `externalId`) are the ones that matter for the requester's use case regardless of what else the object contains.

## Tech design

### Conclusion

Add a third tool function to `src/pax8_mcp/tools/companies.py`, calling the existing generic `Pax8Client.get()` against `/companies/{company_id}`. No new dependency, no client changes, no gateway/control-plane change — this is a same-shape addition next to `pax8_list_company_contacts`, which already takes a single `company_id` path parameter.

### Data & API contract

- API: `GET https://api.pax8.com/v1/companies/{company_id}` (base URL and path pattern per `DEFAULT_BASE_URL = "https://api.pax8.com/v1"`, `src/pax8_mcp/api_client.py:5`, and the ticket's own evidence line "HTTP 方法与端点：GET https://api.pax8.com/v1/companies/{company_id}"). Confirmed against the vendor's public API reference (`https://devx.pax8.com/reference/findcompanies`, fetched during this design): the "Companies" API group is documented as able to "fetch a list of your company records, or a specific company by its companyId" — consistent with a `GET /companies/{companyId}` single-resource endpoint existing alongside the documented `GET /companies` list endpoint. The exact dedicated reference page for the single-company endpoint was not directly reachable during this design (see Open questions); the dev leg should hit a sandbox/real Pax8 account once available (or capture a fixture from the Rewst flow's own history if accessible) to pin the exact response field set before merging the fixture-backed tests.
  - Request: path parameter `company_id` (string, required, Pax8 company UUID per the ticket's example `{{ ORG.VARIABLES.pax_company_id }}`). No query parameters, no request body — a plain GET.
  - Request headers to Pax8 (unchanged, from `Pax8Client._headers()`, `api_client.py:32-36`): `Authorization: Bearer <token>`, `Content-Type: application/json`.
  - Response (200): a single company JSON object. Minimum fields this ticket cares about (named directly in the gap-register evidence): `id`, `name`, `status`, `externalId`. The vendor's OpenAPI "Companies" schema (per the public reference fetched during this design) additionally documents `address`, `phone`, `website`, `billOnBehalfOfEnabled`, `selfServiceAllowed`, `orderApprovalRequired`, `updatedDate`, `contacts` — the tool returns the object as-is (see Open questions on field filtering), so none of this needs to be special-cased in code.
  - Response (404): Pax8 returns an error body; `Pax8Client._raise_for_status` (`api_client.py:53-59`) turns any 4xx/5xx into `Pax8Error(status_code, detail)`, and the tool's `except Pax8Error as e: return f"Error {e.status_code}: {e.message}"` turns that into the same structured-error string format already used by the 9 existing tools.
  - Backward compatibility: purely additive — no existing tool's signature, return shape, or error format changes. MCP clients that already call the other 9 tools are unaffected.

### Key flow / sequence

1. AI client calls `POST /mcp` with `tools/call` → `name: "pax8_get_company"`, `arguments: {"company_id": "<id>"}`, and header `X-Pax8-Token: <token>` (gateway mode, production).
2. `GatewayTokenMiddleware` (`server.py:36-79`) reads the header; if absent, returns 401 before the tool runs (unchanged, applies to every tool including the new one).
3. The tool's `client_factory()` resolves a `Pax8Client` from the per-request `contextvars` token (`server.py:24-33`).
4. The tool calls `client.get(f"/companies/{company_id}")` → `Pax8Client.get()` issues `GET https://api.pax8.com/v1/companies/{company_id}` with `Authorization: Bearer <token>`.
5. On 200: the tool returns `json.dumps(result, indent=2)`. On 4xx/5xx: `Pax8Error` is raised and caught, returning `"Error {status}: {message}"`.

### Non-functional

- Idempotency & concurrency: `GET` is naturally idempotent; no new state is introduced. Per-request token isolation via `contextvars` (`server.py:19-21`) already covers concurrent calls from different tenants/requests — nothing new is needed for this single additional read tool.
- Performance: single lightweight GET of one resource, no pagination, no N+1 pattern. No performance concern beyond what the 9 existing tools already have.
- Security: credentials are never stored or logged — same per-request header pattern as every other tool in this repo (SOP's "credentials only from request headers, no shared state" rule); the new tool does not add any new credential-handling code path.
- Multi-tenant isolation: the Pax8 partner token itself scopes which companies are visible (Pax8-side ACL); this MCP does not add a second isolation layer on top, which matches exactly how the 9 existing tools already work — no change in isolation model.
- Observability: this repo has no structured logging today (confirmed: no logging calls in `tools/companies.py`, `api_client.py`, or `server.py` beyond the one `print(..., file=sys.stderr)` diagnostic in `server.py:109-112` for the no-credentials case). The new tool follows the same (currently minimal) convention — errors are visible to the caller via the returned `"Error {status}: {message}"` string, which is the existing debugging mechanism for this repo.
