## Requirement understanding

One line: Add a pax8_get_product tool to the Pax8 MCP connector that looks up a product by id (name, vendor, SKU) so order subscriptions can be mapped to M365 products, matching the Rewst flow's existing pax8.get_product action.

Ginko IT's Rewst automation calls Pax8's `GET /v1/products/{id}` directly, today, through two Rewst actions executed a combined ~28 times over the last 365 days (`Pax8: Get License Counts` ×17, `Pax8: Get Product` ×11 — evidence grade B per the gap register) to resolve a subscription's product (name, vendor, SKU) so it can be mapped to an M365 product. This is item 33 of `mspbots-gap-register.xlsx` (Rewst → MSPbots migration gap list): a **tool gap**, not a connector gap — the MSPbots Pax8 connector (`MSPbotsAIFramework/pax8-mcp`) already exists and is reachable, but it exposes nine `list_*` tools and no "get one product by id" tool. Success is a new `pax8_get_product(product_id)` MCP tool on that same connector returning at least `id`, `name`, `vendorName`, `shortDescription`, `sku`, so this Rewst flow can be retired in favor of the Agent-platform connector.

## Product design

### Goals / Non-goals

**Goals**: add one new MCP tool, `pax8_get_product`, to the existing `pax8-mcp` connector, so an Agent-platform caller (including a Rewst flow migrated onto this connector) can fetch a single Pax8 product's `id`/`name`/`vendorName`/`shortDescription`/`sku` (and the other fields Pax8 returns) by `product_id`, without needing Pax8's direct partner API.

**Non-goals**: this ticket does not fix the platform-level Pax8 OAuth connect defect (current state, wiki P-2) — that is a platform/control-plane issue, not something the vendor connector repo can fix. It does not touch any of the 9 existing tools. It does not add Pax8's related product endpoints that nobody asked for (provisioning details, product dependencies, pricing) — those are separate Pax8 endpoints with no request behind them in this ticket.

### Acceptance criteria AC1..AC5

- **AC1**: Given a `product_id` that exists in Pax8's catalog, When `pax8_get_product(product_id)` is called with valid credentials, Then the tool returns the Pax8 product record as a JSON string containing at least `id`, `name`, `vendorName`, `shortDescription`, `sku` (the fields the Rewst flow consumes).
- **AC2**: Given Pax8 returns a non-2xx response for the call (e.g. `404 Not Found` for an id that doesn't exist, or a `5xx`), When `pax8_get_product(product_id)` is called, Then the tool returns a readable `Error {status}: {message}` string — the same shape every other tool in this repo already returns — never an unhandled exception/stack trace, and the error text never contains the caller's Pax8 access token.
- **AC3**: Given no Pax8 credentials are available for the current request (gateway mode: no `X-Pax8-Token` header; env mode: `PAX8_API_TOKEN` unset), When `pax8_get_product(product_id)` is called, Then the tool returns the same "no token configured" message the other 9 tools already return, and Pax8 is never called.
- **AC4**: Given the tool's declared MCP schema, When a caller omits `product_id` on `tools/call`, Then the call is rejected as a parameter-validation error before any outbound call to Pax8 (`product_id` has no default value, matching the vendor endpoint's own required path parameter).
- **AC5**: Given two concurrent `pax8_get_product` calls arrive with two different `X-Pax8-Token` values (two different Pax8 partner accounts), When both are in flight at the same time, Then each call's outbound request to Pax8 carries only its own token — no credential bleed between concurrent requests.

### Open questions

- [assumed, non-blocking] The ticket's "return fields (used by the flow)" note (`id`, `name`, `vendorName`, `shortDescription`, `sku`) is read as *the fields the Rewst flow happens to consume today*, not an instruction to filter the tool's output to only those fields. This design assumes the new tool returns the full raw Pax8 response unfiltered, exactly like all 9 existing `list_*` tools (`json.dumps(result, indent=2)`, see `products.py:43`) — that is the established pattern in this repo and avoids silently dropping fields a future caller might need (e.g. `description`, `requiresCommitment`). If product/requester actually wants a trimmed response, that is a small follow-up change to the one new function; it does not affect AC1-AC5 as written (which only require the five named fields to be *present*, not that others be absent).
- [non-blocking] The platform-level Pax8 OAuth connect defect (current state, wiki P-2) means the connector can't be authorized from the platform UI today. This doesn't block shipping the tool (Rewst and other gateway-header callers are unaffected), but it does mean a human verifying this ticket from the platform UI's "Connect" button will hit the same pre-existing wall — called out so it isn't mistaken for something this ticket broke.

## Tech design

### Conclusion

Add one function, `pax8_get_product(product_id: str) -> str`, inside the existing `src/pax8_mcp/tools/products.py`, registered through the `register()` function that `server.py` already calls. It reuses the existing generic `Pax8Client.get()` against `/products/{product_id}` — no new HTTP client code, no new dependency, no schema or config change. This is the smallest possible change that matches the repo's established one-function-per-tool, one-file-per-resource shape.

### Where the current implementation lives

- `src/pax8_mcp/tools/products.py:1-46` — the file the new tool is added to; `pax8_list_products` (`:13-46`) is the pattern to extend (decorator, docstring, `client_factory()` null check, `try/except Pax8Error`).
- `src/pax8_mcp/tools/companies.py:38-58` — `pax8_list_company_contacts`, the closest existing example of a tool with a required path-id parameter rather than only query filters; the new tool's signature is modeled on this one, not on the paginated list tools.
- `src/pax8_mcp/api_client.py:16-59` — `Pax8Client`, unmodified. `.get(path, params)` (`:43-51`) already supports any path, including a path-parameter-interpolated one like `/products/{product_id}`.
- `src/pax8_mcp/server.py:82-125` — `create_mcp_server()`; `products.register(mcp, client_factory)` (`:122`) is already wired, so the new tool becomes available with no change to this file.
- `src/pax8_mcp/config.py` — no change; auth-mode/header handling is unaffected.
- `README.md` — Tool List table (`## Tool List`) needs a new row for `pax8_get_product`, and the MSPbots Connector section (added at `f71ce7a`) must stay byte-identical to `~/.claude/skills/vendor-mcp-development/reference/readme-connector-section.md` per SOP — the dev leg touches only the Tool List table, not the Connector section.

### Data & API contract

**Outbound (Pax8 vendor API, unchanged client code, new call site only)**:

```
GET https://api.pax8.com/v1/products/{productId}
Headers: Authorization: Bearer <token>        (added by Pax8Client._headers(), existing, unmodified)
Path param: productId  (string, UUID)  — required

200 response body (per https://devx.pax8.com/reference/findproductbyproductid.md, verified 2026-10-30):
{
  "id": "uuid",
  "name": "string",
  "vendorName": "string",
  "shortDescription": "string",
  "description": "string",
  "sku": "string",
  "vendorSku": "string",
  "altVendorSku": "uuid (deprecated, legacy Microsoft SKU)",
  "requiresCommitment": true
}

404: product not found, body shape not pinned by Pax8's docs beyond a message;
     handled generically by the existing Pax8Error(status_code, message)
```

**Inbound (new MCP tool contract)**:

```
Tool: pax8_get_product
Input:  { "product_id": "<string, required>" }
Output (success): the raw Pax8 response above, JSON-serialized with indent=2
                   (same shape convention as all 9 existing list_* tools — no field filtering)
Output (vendor error, any non-2xx): "Error {status_code}: {message}"
Output (no credentials): "Error: No Pax8 token configured. Set PAX8_API_TOKEN or use AUTH_MODE=gateway."
```

**Backward compatibility**: purely additive — no existing tool name, parameter, or response shape changes. No database involved (this repo is stateless, no DB). No migration, no backfill.

### Key flow / sequence

```
MCP client --(X-Pax8-Token header)--> GatewayTokenMiddleware (server.py:36-79, unchanged)
  --stores token in contextvar (server.py:19-21, unchanged)--> tools/call pax8_get_product(product_id)
  --> client_factory() --> get_client_from_context() (server.py:24-33, unchanged) --> Pax8Client(token, ...)
  --> client.get(f"/products/{product_id}")  (api_client.py:43-51, unchanged)
  --> GET https://api.pax8.com/v1/products/{product_id}  (Authorization: Bearer <token>)
  <-- 200 product JSON, or non-2xx --> Pax8Error(status_code, message)
  --> tool returns json.dumps(result, indent=2), or f"Error {status}: {message}"
```

Every step except "the new tool function calls `client.get(...)` and formats the result" already exists and is exercised today by the other 9 tools.

### Non-functional

- **Idempotency & concurrency**: a read-only `GET` by primary key is naturally idempotent. No new shared/mutable state is introduced — the tool reuses the same per-request `client_factory()` / `contextvars` isolation every other tool already relies on (`server.py:19-33`), so concurrent calls with different tokens stay isolated (AC5 / TC-PAX8-006).
- **Performance**: single-resource GET by id, no pagination needed; expected latency and payload size are smaller than any of the existing `list_*` calls. No caching added — consistent with the rest of this stateless repo.
- **Security**: credential handling is unchanged — the token is still only ever read from the per-request header/contextvar (SOP's "no global state" rule), never logged, never defaulting from the environment except in the pre-existing local `AUTH_MODE=env` dev mode. `Pax8Error.message` is built from the vendor's response body/text, which does not echo the request's `Authorization` header, so the new tool does not introduce a new token-leak surface (AC2 / TC-PAX8-003 tests this explicitly).
- **Multi-tenant isolation**: this repo has no MSPbots-side tenant concept of its own; the vendor-account boundary is the token itself, isolated per request by the existing contextvar mechanism (unmodified by this ticket).
- **Observability**: no new logging added — none of the 9 existing tools log request/response bodies either, so this keeps the same (lack of) footprint. A repo-wide audit-logging decision, if ever made, is out of this ticket's scope.
